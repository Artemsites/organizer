## Неочевидные находки

### 2026-09-16: Приёмка по DoD прошла, а половина DoD не выполнена — почему
- **Проблема**: Шаг 7b закрыт `[x]`, но аудит по вопросу хозяина «все дефекты запланированы?» нашёл в нём stored XSS (`escapeHtml` не экранирует кавычки, результат идёт в атрибут `aria-label`), неработающий `AbortController` (`client.ts` не принимает `signal`) и утечку detached DOM (`filterClickListener` не снимается). Все три пункта были прямо записаны в DoD Шага 7b.
- **Причина пропуска**: два теста в `web/test/todos-module.test.ts` названы как проверки этих пунктов, но проверяют другое. Тест «защита от XSS» смотрит только `<span class="todo-app__text">` — место, где экранирование и так работает, и payload в нём без кавычки. Тест «`destroy()` отменяет активные запросы через `AbortController`» проверяет `badgeCount() === 0`. Оба зелёные, оба ничего не доказывают.
- **Вывод на будущее**: имя теста — это обещание, а не проверка. При приёмке шага читать **тело** теста и спрашивать: «на каком изменении кода этот тест покраснеет?». Если ответ «ни на каком из тех, что он называет» — тест ложно-зелёный, а шаг не принят.
- **Следствие для процесса**: в DoD шага писать не «покрыто тестом», а какой именно код должен сломать тест. Заведено Шагом 7b.1.4, там же это разбирается как учебный материал по видам тестирования.

### 2026-09-16: Node-половина темы Event Loop (вывод Шага 15.1, код не трогали)
- **Проблема**: `croner`-джоба Шага 8a может позвать синхронный `zx` (или `execSync`) — весь Node-процесс встанет на время команды: timers, poll и check очереди loop не крутятся, web-запросы к ядру висят.
- **Вывод**: фоновые задачи — только асинхронно (`await $`...`` из `zx`, `child_process` с колбэком), тяжёлое — чанками с уступкой loop (`setImmediate` между порциями). Браузерная половина того же правила: DOM до `await`, сеть после.

### 2026-09-16: rAF-батчинг со снапшотом в момент вызова пишет протухшие данные (фикс Шага 15.2)
- **Проблема**: `updateCounters()` снимал `statusCounts()` до планирования кадра. Вызов из `init()` видел пустой `Map`, а свежий вызов из `load()` отбрасывался коалесингом — rAF писал нули навсегда, тест `Все (2)` падал.
- **Вывод**: при coalescing читать состояние строго внутри кадра (last state wins). Снапшот-в-момент-вызова корректен только без схлопывания.

### 2026-09-16: Мёртвая сущность выглядит как сделанная работа

- **Проблема**: таблица `reminders` лежала в схеме с первого дня и создавалась при каждом старте. Её видно в `schema.ts`, она упоминалась в замысле Шага 8a («таблицы уже есть в схеме») — и на этом основании шаг считался наполовину подготовленным. Методов к ней не было ни одного.
- **Вывод**: «сущность объявлена» и «сущность используется» — разные вещи, и первое маскирует второе. Проверка стоит одного `grep` по имени таблицы за пределами файла схемы. Тот же признак был у `BacklogItem` (Шаг 9.1).
- **Следствие**: при планировании шага по существующей схеме сперва грепаем сущность, потом опираемся на неё.

### 2026-09-16: Passenger усыпит `croner` вместе с приложением

- **Проблема**: на Beget приложение без входящих запросов засыпает. Планировщик живёт внутри того же процесса, значит напоминания просто не сработают, при этом сервис отвечает на первый же запрос и выглядит исправным.
- **Вывод**: внутрипроцессный планировщик на shared-хостинге — не источник времени, а лишь ускоритель. Источником должен быть внешний cron, который будит приложение, а приложение обязано уметь догнать всё просроченное, а не выполнить «то, что пришлось на эту минуту».
- **Следствие**: догон просроченных напоминаний заложен в Шаг 8a.3 как обязательный механизм, а не страховка; внешний cron — Шаг 12.2.
