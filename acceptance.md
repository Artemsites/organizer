# Приёмка: Шаг 8a — `reminders`, серверная часть

Чекбоксы ставит **приёмщик**, не исполнитель. Пункт закрывается своим доказательством, а не пересказом шага.

Прогон: `npm --prefix server test`. Полный прогон: `npm test`. Сборка: `npm run build`.

## Модель данных (8a.1)

- [x] Мёртвой сущности напоминаний в системе больше нет
  WHEN выполнен поиск имени таблицы `reminders` по всему репозиторию
  THEN ни одного обращения к ней нет, включая файл схемы, а хранилище поднимается и работает

- [x] Одно напоминание нельзя запланировать дважды
  WHEN для одного события дважды записывается срабатывание на один и тот же момент
  THEN вторая запись отклоняется хранилищем, а не прикладным кодом

- [x] Удаление события уносит его срабатывания
  WHEN событие удаляется через `DELETE /api/v1/events/:id`
  THEN строк журнала с этим событием не остаётся, и удаление не требует отдельного вызова из роута

- [ ] Журнал не растёт бесконечно
  WHEN в журнале есть выданные строки старше срока хранения и фоновая задача отработала
  THEN эти строки удалены, а невыданные и свежие сохранены

## Валидация записи событий (8a.2)

- [x] Лишние поля не доезжают до хранилища
  WHEN `POST /api/v1/events` приходит с полями `id` и `createdAt` в теле
  THEN эти значения не попадают в ответ и не попадают в базу, а созданная запись получает собственные значения

- [x] Событие не может кончиться раньше, чем началось
  WHEN `POST /api/v1/events` приходит с концом раньше начала
  THEN ответ 400, в базе ничего не создано

- [x] Границы длины и типов держатся
  WHEN приходит заголовок в 10 000 символов, либо нецелая метка времени, либо интервал напоминания за пределами допустимого
  THEN на каждый случай ответ 400, в базе ничего не создано

- [x] Валидация событий и задач сделана одним подходом
  WHEN сравниваются `server/src/routes/events.ts` и `server/src/routes/tasks.ts`
  THEN оба маршрута валидируют через схемы из `server/src/routes/schemas.ts`, ручных проверок «поле не пустое» в роуте событий не осталось

## Срабатывание и догон (8a.3)

- [x] Напоминание срабатывает ровно один раз
  WHEN событие с интервалом напоминания наступило и фоновая задача отработала дважды подряд
  THEN выдана ровно одна строка журнала, вторая отработка не выдаёт ничего

- [x] Перезапуск не порождает повтор
  WHEN сервер перезапущен после уже выданного напоминания и фоновая задача отработала
  THEN повторной выдачи нет

- [x] Простой не теряет напоминания
  WHEN время смещено на три часа вперёд, за которые пришлись четыре момента срабатывания, и фоновая задача отработала один раз
  THEN выданы все четыре, а не только попавшее в текущую минуту

- [x] Снятие напоминания отменяет невыданное срабатывание
  WHEN у события убран интервал напоминания до момента срабатывания
  THEN невыданная строка журнала исчезает, и напоминание не приходит

- [x] Фоновая задача не останавливает сервер
  WHEN фоновая задача выполняется
  THEN обработчик не содержит синхронных вызовов внешних команд, и запрос к API во время её работы обслуживается

- [x] Журнал доставки не растёт бесконечно
  WHEN фоновая задача отработала при наличии выданных строк старше срока хранения
  THEN эти строки в журнале отсутствуют, а невыданные и свежие остаются; уборка вызвана из джобы, а не из теста

- [x] Оба входа записи события планируют напоминание
  WHEN событие с интервалом напоминания создано через `POST /api/v1/events`, и отдельно — прислано через `POST /api/v1/sync`
  THEN в обоих случаях в журнале появляется срабатывание с одинаково вычисленным моментом

- [ ] Синхронизация не планирует по мусорным данным
  WHEN в `POST /api/v1/sync` приходит событие с отрицательным, нецелым или запредельным интервалом напоминания
  THEN запись отклонена, в журнале нет ни одной строки по этому событию
  - не принято (2026-09-18): `server/src/routes/sync.ts:10` по-прежнему берёт тело как `as SyncPayload`, схем нет — Шаг 8a.3.0 (`plan.md:93`) не выполнен, а хук планирования уже стоит в `upsertEvent` (`server/src/db/index.ts:603`). Мусорный `reminderMinutes` из синхронизации доходит до `planEventReminder` без проверки.

## Поток доставки (8a.4)

- [ ] Сработавшее напоминание доезжает до подключённого клиента
  WHEN клиент подключён к `GET /api/v1/reminders/stream` и наступает момент срабатывания
  THEN клиент получает кадр с идентификатором и данными события, без опроса со своей стороны

- [ ] Обрыв не теряет и не дублирует
  WHEN клиент переподключается, передав идентификатор последнего полученного кадра
  THEN он получает только то, что пропустил, и ни одного повтора

- [ ] Два подписчика не получают одно напоминание дважды каждый
  WHEN к потоку подключены два клиента и наступает одно срабатывание
  THEN строка журнала помечается выданной один раз, повторной выдачи того же срабатывания не происходит

- [ ] Поток закрывается без следов
  WHEN соединение закрыто клиентом
  THEN подписка снята, периодический heartbeat остановлен, счётчик активных потоков вернулся к прежнему значению

- [ ] Молчащий поток не рвётся
  WHEN событий нет дольше интервала простоя
  THEN соединение живо, потому что сервер шлёт heartbeat

- [ ] Число потоков ограничено
  WHEN открыто больше потоков, чем разрешено на токен
  THEN лишнее подключение отклоняется, уже открытые продолжают работать

- [ ] Поток закрыт авторизацией
  WHEN запрос к потоку приходит без `x-client-token` или с неверным
  THEN соединение не устанавливается, данные событий не отдаются

- [ ] Токен не утёк в адрес запроса
  WHEN просмотрены маршрут потока и то, как к нему обращается клиент
  THEN токен передаётся заголовком, в строке запроса его нет ни в одном месте
