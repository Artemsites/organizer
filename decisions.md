# Органайзер: Decisions (ADR)

Неочевидные находки и грабли — [memory.md](./memory.md). Шаги — [plan.md](./plan.md). Техдолг — [issues.md](./issues.md).

### 2026-09-14: Выбор npm workspaces для монорепозитория
- **Проблема**: В плане упоминался `pnpm workspaces`, однако в основном проекте и окружении используется стандартный `npm`.
- **Решение**: Настроили `npm workspaces` в корневом `package.json` (`server`, `cli`, `web`, `shared`).
- **Причина**: Нативность из коробки, отсутствие необходимости ставить сторонний пакетный менеджер, 100% совместимость с Node.js.

### 2026-09-14: Использование встроенного модуля `node:sqlite` (WAL)
- **Проблема**: Необходимость легковесной встроенной БД без необходимости поднимать отдельный сервер PostgreSQL/MySQL.
- **Решение**: Использовать встроенный в Node.js 22.5+ синхронный модуль `DatabaseSync` из `node:sqlite` с режимом WAL (`PRAGMA journal_mode = WAL;`).
- **Причина**: Нулевой оверхед, нет компиляции нативных бинарников (в отличие от `better-sqlite3`), максимальная скорость чтения/записи.

### 2026-09-14: Архитектурное разделение CLI-воркера и Web UI
- **Проблема**: Необходимость как удобного графического интерфейса для человека, так и возможности автоматизации системных задач (скрипты, brew, puppeteer).
- **Решение**: Выделены два независимых клиента: `organizer/cli` (консоль + локальный агент-воркер на Mac) и `organizer/web` (визуальный SPA на чистом DOM/TS/SCSS без фреймворков). Оба общаются с ядром через единый REST API.
- **Причина**: Удаленный сервер не может исполнять bash-команды на локальной машине пользователя. Воркер на Mac закрывает эту задачу.

### 2026-09-14: Приоритет локальной разработки на Mac перед Beget
- **Проблема**: Шаг 1 плана требовал проверки хостинга Beget и Passenger.
- **Решение**: Деплой на Beget перенесен в Шаг 9 (финальный), вся первичная разработка и TDD-тестирование ведутся локально на macOS.
- **Причина**: Ускорение цикла обратной связи и отладки архитектуры без сетевых задержек и зависимостей от удаленного хостинга.

### 2026-09-14: Транспорт Web → Ядро — прокси Vite, а не CORS
- **Проблема**: Web (`:5173`) и ядро (`:3000`) на разных origin. Нужен доступ к REST API, при этом `X-Client-Token` — общий секрет, и в бандле браузера он виден любому, кто открыл страницу (принцип 0 spec.md).
- **Решение**: `server.proxy` в `web/vite.config.ts`, логика вынесена в `web/vite.proxy.ts` (`createApiProxy`). Токен подставляет сам прокси на событии `proxyReq`, читая его через `loadEnv(mode, <корень репо>, '')`. Пакет `@fastify/cors` не ставится.
- **Причина**: Same-origin снимает CORS и preflight целиком (быстрее), а секрет остаётся в Node-процессе Vite и в клиентский код не попадает. Проверено: сборка прогрепана на тестовый токен — пусто.
- **Запрет**: токен никогда не читать через `import.meta.env` / `VITE_*` — такие переменные Vite встраивает в бандл.

### 2026-09-14: Конфигурация — один `.env` в корне, без пакета `dotenv`
- **Проблема**: Секреты нужны и серверу, и конфигу Vite; два источника разъедутся.
- **Решение**: Один `.env` в корне монорепо (в `.gitignore`), образец — `.env.example`. Сервер читает его нативным флагом Node `--env-file-if-exists`, Vite — через `loadEnv` с пустым префиксом.
- **Причина**: Нативный механизм вместо зависимости (принцип 2.1 spec.md). Проверено на Node 24.

### 2026-09-14: Драйвер браузерной автоматизации — `playwright` вместо `puppeteer-core`
- **Проблема**: Плагину `browser-automation` нужно надёжно работать вместо человека на JS-сайтах.
- **Решение**: `playwright`. `spec.md` §1/§3/§3.7 обновлён по разовому разрешению хозяина.
- **Причина**: Скорость у обоих одинаковая — её задаёт Chromium, а не библиотека. Решают авто-ожидания (у puppeteer каждый клик обрастает ручными `waitFor`, и именно они флакуют на медленном сайте), дешёвые изолированные контексты и `storageState` для переиспользуемого логина.
- **Следствие**: требование локально установленного Chrome снимается — Playwright ставит браузеры своей командой `install`.

### 2026-09-14: Сборщик фронтенда — Vite, Gulp вычеркнут
- **Проблема**: `TODO.md` требовал навык Gulp («у нас Gulp»), `spec.md` и написанный код — Vite. Оба файла P0.
- **Решение**: Vite. Gulp из списка навыков убран хозяином.
- **Причина**: Второй сборщик в проекте, объявленном минималистичным, противоречит принципу 2. Навык Gulp при надобности отрабатывается в отдельном репозитории.

### 2026-09-14: GSAP — только там, где нативного не хватает
- **Проблема**: `TODO.md` требует навык GSAP (таймлайны, ScrollTrigger), `spec.md` §2.1 требует нативное там, где оно эффективно.
- **Решение**: По умолчанию CSS-переходы, `@keyframes` и Web Animations API. GSAP подключается по факту упора — сложные секвенции и ScrollTrigger, в первую очередь на лендинге (статика, бюджет ядра не тратится).

### 2026-09-15: Валидация входных данных через Zod и защита от Mass Assignment
- **Проблема**: В `server/src/routes/tasks.ts` проверялось только наличие `title`. В SQLite можно было передать невалидный статус (`'lol'`), строковую дату или перезаписать поля.
- **Решение**: Вынесли схемы в `server/src/routes/schemas.ts` (`createTaskSchema`, `updateTaskSchema`). Валидация через `schema.safeParse` на границе API, в БД передаются только очищенные данные (`parsed.data`), лишние поля вычищаются (`strip`). Пустой PATCH `{}` отклоняется (400).
- **Причина**: Целостность данных — принцип 0 spec.md. Zod уже был в зависимостях проекта.

### 2026-09-15: Имена и сокращения в коде
- **Проблема**: `stmt` без расшифровки, тесты названы номером шага.
- **Решение**: общепринятое сокращение (`stmt` = statement) — сразу комментарий, что значит; иначе полное имя. `describe`/`it` — что проверяет тест, не номер шага из плана.

### 2026-09-15: Модульная SCSS-архитектура (abstracts/ с картами и @forward фасадом)
- **Проблема**: Стили были плоскими (`_variables.scss`, `main.scss`), без типизированных структур данных, без миксинов адаптивности, с риском "Z-index Hell" и разрозненных брейкпоинтов.
- **Решение**: Создана структура `web/src/styles/abstracts/`: SCSS Maps (`$breakpoints`, `$z-layers`, `$colors`, `$radii`), чистые функции-геттеры с `@error` валидацией (`bp()`, `z()`, `color()`), миксины Mobile-First (`min-bp` с блоком `@content`) и `hardware-accel`. Публичный API закрыт паттерном "Фасад" через `_index.scss` (`@forward`).
- **Причина**: Single Source of Truth (SSOT), Fail-Fast компиляция (опечатка в брейкпоинте ломает сборку, а не верстку в проде), масштабируемость для последующих модулей.

### 2026-09-15: Типографическая шкала в токенах ($font-sizes и функция fs())
- **Проблема**: В SCSS использовались разрозненные магические числа (`0.75rem`, `0.85rem`, `0.9rem`, `1.15rem`, `1.4rem`), что приводило к визуальной рассинхронизации.
- **Решение**: Добавлена карта `$font-sizes` в `web/src/styles/abstracts/_variables.scss` и функция-геттер `fs($size)` с валидацией в `_functions.scss`. Стили переведены на использование `fs('xs' | 'sm' | 'base' | 'md' | 'xl')`.
- **Причина**: Modular Type Scale (SSOT для типографики), исключение магических чисел, единая система пропорций.

### 2026-09-16: Слой base/ и CSS Custom Properties для рантайм-темизации
- **Проблема**: Значения цветов зашивались в CSS на этапе компиляции (нельзя менять тему Dark/Light без пересборки). При первой итерации в `var(--)` ошибочно завернули всё подряд (радиусы, шрифты, транзишены), а цвета светлой темы захардкодили в `_root.scss`.
- **Решение**: В `abstracts/_variables.scss` вынесены карты `$theme-light` (дефолт) и `$theme-dark` (SSOT). В `base/_root.scss` переменные `--color-*` генерируются циклом `@each`: в `:root` светлая тема по умолчанию, на `[data-theme='dark']` опциональная тёмная. Статические токены (`radius()`, `$font-sans`, `$transition-base`) возвращены в compile-time SCSS без рантайм-оверхеда.
- **Причина**: Чёткое разделение Run-Time (только меняющиеся цвета темы) и Compile-Time (статическая геометрия и анимации), устранение оверинжиниринга и дублирования.

### 2026-09-16: Адаптивный лейаут AppShell, Drawer и CSS Logical Properties
- **Проблема**: Лейаут был зашит жестко в `main.scss` с двухколоночным гридом (`260px 1fr`), что на мобильных экранах (< 768px) вызывало горизонтальное переполнение и ломало мобильный UI. Отсутствовала мобильная навигация.
- **Решение**:
  1. Лейаут выделен в компонент `web/src/styles/components/_app-shell.scss` с фасадом `components/_index.scss`.
  2. Все отступы и границы переведены на CSS Logical Properties (`padding-inline/block`, `margin-inline/block`, `inset-block`, `inset-inline-start`, `border-inline-end`).
  3. Реализован Mobile-First Off-Canvas Drawer: на экранах `< 768px` сайдбар скрыт за левым краем (`transform: translateX(-100%)`) с аппаратным ускорением GPU (`@include hardware-accel`), открывается по клику на гамбургер-кнопку (минимальная зона тача 44x44px по гайдлайнам UX) и выводит полупрозрачный бэкдроп (`.sidebar__backdrop`).
  4. На десктопе (`@include min-bp('md')`) сайдбар автоматически встает в нормальный поток двухколоночной сетки, кнопка меню и оверлей скрываются (`display: none`).
  5. Поддержана доступность (a11y): атрибуты `aria-expanded`, `aria-label`, `aria-controls`, закрытие по клавише `Escape`, клику на подложку и автоматическое закрытие при переходе между модулями.
- **Причина**: Полноценный адаптив без сторонних библиотек, соблюдение принципов Mobile-First, Zero Nesting BEM и 60 FPS производительности.

### 2026-09-16: Слой компонентов, 60fps-анимации и clip-path
- **Проблема**: Стили кнопок, инпутов и карточек были объявлены в `main.scss`. Ховеры меняли `background-color`, триггеря Repaint. Отсутствовали декоративные элементы со срезанными углами на чистом CSS.
- **Решение**:
  1. Созданы компоненты `_button.scss`, `_input.scss`, `_card.scss` в `web/src/styles/components/` с фасадом `_index.scss`. `main.scss` очищен до чистой сборки слоёв (`abstracts`, `base`, `components`).
  2. Ховер кнопок переведён на `Paint = 0`: анимация `opacity` у псевдоэлемента `::before` (Compositor-only) с тактильным откликом `:active { transform: scale(0.97) }`.
  3. В карточках (`.card--chamfered`) реализованы срезанные углы через `clip-path: polygon(...)`, компилируемый на GPU без перерисовки контуров границ.
  4. В `todos.scss` внедрены аппаратные микро-сдвиги `transform: translateX(3px)` и плавный `opacity: 0.55` при завершении задачи.
- **Причина**: Архитектура SCSS 7-1, исключение Repaint/Layout thrashing при взаимодействии с UI, чистый BEM без вложенности.

### 2026-09-16: Токенизация интеракций и библиотека безопасных GPU-миксинов
- **Проблема**: В компонентах плодились "магические числа" тактильного отклика (`scale(0.95)`, `scale(0.97)`, `scale(0.88)`), а правила GPU-композитинга (`isolation: isolate`, `opacity` на `::before`, `visibility: hidden` на оверлеях) приходилось писать руками, что приводило к дублированию и риску ошибок (Layer Over-Promotion, утечки VRAM).
- **Решение**:
  1. В `abstracts/_variables.scss` вынесены карты токенов `$scales` (`press-subtle`, `press-base`, `press-deep`) и `$shifts` (`hover-x`, `lift-y`), добавлены геттеры `scale()` и `shift()` с fail-fast валидацией в `_functions.scss`.
  2. В `abstracts/_mixins.scss` создана библиотека типовых GPU-миксинов: `gpu-press` (тактильный отклик на GPU), `gpu-hover-fade` (ховер без Repaint через псевдоэлемент), `gpu-hover-lift` (подъем карточки на GPU) и `gpu-overlay` (полноэкранная подложка без Over-Promotion).
  3. Компоненты (`_button.scss`, `_card.scss`, `_app-shell.scss`, `todos.scss`) переведены на вызовы этих миксинов.
- **Причина**: Инкапсуляция правил GPU-рендеринга в единый источник правды (SSOT), полное устранение "магических чисел", декларативный чистый код компонентов.

### 2026-09-16: Предотвращение CSS Shorthand Clobbering в GPU-миксинах
- **Проблема**: В `todos.scss` и `_button.scss` объявление `transition` (color, background, border-color) затиралось (clobbered) шортхэндом `transition: transform ...` внутри `@mixin gpu-press`. Кроме того, на статичной кнопке фильтра висел избыточный `@include hardware-accel`, вызывавший лишний Repaint текстуры в VRAM при смене фона ховером.
- **Решение**:
  1. `@mixin gpu-press` дополнен поддержкой Varargs (`$extra-transitions...`), объединяющим сопутствующие переходы с `transform` в один CSS `transition`.
  2. Убран избыточный `hardware-accel` со статичных кнопок табов фильтра (`.todo-app__filter-btn`).
- **Причина**: Ликвидация багов затирания CSS transitions, предотвращение Layer Over-Promotion и лишних накладных расходов VRAM.

### 2026-09-16: Устранение оверинжиниринга: отказ от миксинов min-bp/max-bp в пользу нативного @media
- **Проблема**: Миксины `@include min-bp('md')` и `@include max-bp('md')` представляли собой избыточную абстракцию (Unnecessary Wrapper / Leaky Abstraction), которая скрывала стандартный CSS `@media`, ломала свободную композицию условий (например `and (orientation: landscape)`) и заставляла учить кастомный DSL вместо знания платформы.
- **Решение**:
  1. Удалены миксины `min-bp` и `max-bp` из `web/src/styles/abstracts/_mixins.scss` и из глобальных примеров `~/.agents/examples/front/scss/mixins/`.
  2. Все медиа-запросы в `_app-shell.scss` переведены на нативный синтаксис CSS `@media (min-width: bp('md'))` с сохранением типобезопасного SSOT геттера.
  3. Обновлены глобальные правила `AGENTS_FRONTEND.md`.
- **Причина**: Принцип KISS & YAGNI, прямое использование возможностей платформы без лишних обёрток.

### 2026-09-15: Статус по умолчанию — `backlog`, не `todo`
- **Проблема**: `createTask` без `status` писал `todo`, хотя жизненный цикл в spec.md §2 начинается с `backlog`.
- **Решение**: `dto.status ?? 'backlog'` и `DEFAULT 'backlog'` в SQL. Согласовано с хозяином.
- **Причина**: задача рождается как идея; в `todo` её двигает человек.

### 2026-09-15: CHECK на tasks — снос локальной БД, не миграция
- **Проблема**: `CREATE TABLE IF NOT EXISTS` не добавит `CHECK (status/priority)` на уже созданную таблицу.
- **Решение**: снести локальный `organizer.db`. Файла не было (сервер в dev часто на `:memory:`, путь в `.gitignore`). Схема поднимется при следующем старте с диском.
- **Причина**: данных нет, миграция дороже сноса. Когда появятся данные — понадобится `ALTER`/`rebuild table`, не раньше.

### 2026-09-15: Hardening ядра — защита от перебора токена, DoS диска и утечки в логи
- **Проблема**:
  1. Неограниченный перебор токена скриптами.
  2. Залив задач бесконечным циклом скрипта до полного исчерпания места на диске ПК.
  3. Утечка секрета `x-client-token` в логи при включении логгера Fastify.
- **Решение**:
  1. В `server/src/auth.ts` добавлен in-memory rate-limiter: N неудачных попыток с одного IP → HTTP 429 Too Many Requests. Успешный запрос сбрасывает счетчик.
  2. В `server/src/routes/tasks.ts` добавлен hard cap (потолок) задач: проверка `db.getTasksCount() >= maxTasks` (дефолт 2500, согласовано с хозяином), отклонение с ошибкой 400.
  3. В `server/src/index.ts` настроена сериализация `req.headers` и маскирование секрета через Pino `redact` (CWE-532).
- **Причина**: Принцип 0 spec.md (защита ПК пользователя и данных от автоматических агентов и скриптов).

### 2026-09-16: Порядок практики задаёт хозяин, но наблюдателям нужен материал
- **Проблема**: хозяин задал порядок навыков (DOM/Observers → Event Loop → GSAP → UI-модули → Core Web Vitals → ES6+ → TypeScript → анимация → UI-кит → CSS → SCSS → сборщики → CI). Часть навыков нельзя практиковать в заданном порядке: `IntersectionObserver` без длинного списка и `ResizeObserver` без календаря — синтетика.
- **Решение**: Шаг 15 разнесён по плану подшагами, а не стоит одним блоком. 15.1/15.2/15.5 идут сразу (материал — готовый `TodosModule`), 15.3 после Шага 9, 15.4 после Шага 11, 15.7 после production-сборки. Маппинг «навык → шаг» — раздел «Учебная программа» в конце `plan.md`.
- **Причина**: упражнение на выдуманных данных не даёт навыка и оставляет техдолг в проекте. Материал должен появляться из продуктовых шагов.

### 2026-09-16: Webpack вычеркнут, CI — GitHub Actions
- **Проблема**: `TODO.md:29-30` требует навыков Webpack и GitLab CI. Решением от 2026-09-14 сборщик проекта — Vite (Gulp вычеркнут по той же причине), а CI объявлен локальным скриптом без внешней площадки.
- **Решение хозяина 2026-09-16**:
  1. **Webpack вычеркнут**, как раньше Gulp. Пайплайн сборки разбираем на живых `web/vite.config.ts` и `web/vite.proxy.ts`.

### 2026-09-16: Напоминание — свойство события, отдельной сущности `reminders` нет

Таблица `reminders` существовала в `server/src/db/schema.ts` с первого дня и была мёртвой: ни одного метода в `server/src/db/index.ts`, ни одного роута, ни одной модели в `shared/`. Параллельно `events` уже несла `reminder_minutes` — то есть напоминание было описано дважды.

Решение хозяина: таблицу снести. Событие отвечает на «что и когда», `reminder_minutes` — на «за сколько предупредить». Отдельно заводится только служебный журнал доставки (событие, момент срабатывания, состояние) — он нужен не для модели, а чтобы не отправить одно напоминание дважды.

Отвергнуто: держать `reminders` самостоятельной сущностью (две таблицы, два роута, два представления ради случая «напомнить в 15:00», который выражается событием) и слить всё в `tasks.due_date` (тогда календарь теряет события без исполнителя — день рождения, встречу — и `end_time` негде хранить).

Это тот же диагноз, что у `BacklogItem` (Шаг 9.1): вторая модель того же самого. Признак — сущность объявлена, но к ней никто не обращается.

### 2026-09-16: Доставка напоминаний — SSE, не polling и не WebSocket

Поток односторонний: сервер сообщает «сработало», команды клиент и так шлёт обычным HTTP. Под это нужен push, а не дуплекс.

Выбран SSE. В браузере это нативный `EventSource`: переподключение и добор пропущенного по `Last-Event-ID` работают без единой строки нашего кода. В CLI — тот же поток обычным `fetch`. Зависимостей ноль.

Отвергнут **polling**: холостые запросы круглые сутки и задержка до интервала опроса, а в фоновой вкладке браузер душит таймеры.

Отвергнут **WebSocket**: дуплекс здесь не нужен, а цена — зависимости `@fastify/websocket` и `ws`, свой heartbeat и своя логика переподключения. Плюс два узких места в этом конкретном проекте: токен в браузер не попадает, его проставляет Vite-прокси (`web/vite.proxy.ts:19`), и для обычного GET это работает как есть, а для WS нужна отдельная настройка upgrade; на проде (Шаг 12, Passenger на Beget) SSE — просто долгий HTTP-ответ, тогда как WS требует поддержки upgrade у Passenger и nginx. Навык WebSocket честнее учить на двустороннем трафике — кандидат назван в Шаге 10 (синхронизация доски между вкладками).
